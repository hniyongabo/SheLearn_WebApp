Writing a Software Requirements Specification (SRS) Document

Before a single line of code is written, every successful software project starts with a plan. An SRS document is that plan — it defines exactly what the software must do, who it serves, and the constraints it must meet. In this lesson you will learn how to read, understand, and write a professional SRS document from scratch.

1 What is an SRS?

A Software Requirements Specification (SRS) is a formal document that describes everything a software system should do. It acts as a contract between the client (the person who wants the software) and the development team (the people who build it).

Think of it like an architect's blueprint for a house. Before builders lay a single brick, the architect draws every room, every door, every window — in precise detail. An SRS does the same thing for software.

Real-world analogy: Imagine you hired a tailor to make a dress. Without telling them your measurements, color, fabric, and style — they cannot make what you want. The SRS is exactly that conversation, written down in a structured format so nothing is left to guessing.

The SRS standard most commonly followed is IEEE 830, which gives teams a universal structure so any engineer anywhere in the world can read and understand the document.

2 Why It Matters

Many software projects fail — not because the developers weren't skilled, but because nobody clearly defined what needed to be built. Studies consistently show that fixing a requirement error during development costs 10x more than catching it at the requirements stage.

Prevents Misunderstandings

Everyone — client, designer, developer, tester — reads the same document and agrees on what "done" looks like.

Guides Development

Developers use the SRS as a checklist. Each feature gets built to spec, not based on assumptions.

Enables Testing

QA testers write test cases directly from the SRS requirements — no SRS means no clear pass/fail criteria.

Legal Protection

If a client later says "this isn't what I wanted," the SRS is the agreed-upon contract that settles disputes.

3 Key Sections of an SRS

A standard SRS document is divided into these main sections:

1. Introduction

Purpose of the document, scope of the software, definitions of terms, and list of references.

2. Overall Description

Product perspective, product functions, user classes, operating environment, and constraints.

3. Functional Requirements

What the system must DO — every feature and behaviour listed precisely.

4. Non-Functional Requirements

How well the system must perform — speed, security, scalability, accessibility.

5. External Interface Requirements

User interfaces (UI mockups), hardware interfaces, software interfaces (APIs), communication protocols.

6. Appendix

Diagrams, data models, glossary, index — supporting material that doesn't fit in the main sections.

4 Functional Requirements

Functional requirements describe the behaviour of the system — what it should do in response to inputs. They are written as precise, testable statements.

Rule of thumb: A good functional requirement answers — "When [something happens], the system shall [do this]."

Each requirement is given a unique ID so it can be tracked and tested individually. Here is the format:

FR-01: The system shall allow users to register with a name, email, and password. FR-02: The system shall send a confirmation email after successful registration. FR-03: The system shall allow registered users to log in using email and password. FR-04: The system shall redirect users to their track dashboard upon login. FR-05: The system shall allow facilitators to upload new lesson materials. FR-06: The system shall display an error message if login credentials are incorrect.

Rules for Writing Functional Requirements

  • Use "shall" (not "should" or "will") — "shall" means it is mandatory.
  • One requirement per statement — never combine two behaviours in one line.
  • Be specific enough that a tester can write a pass/fail test for it.
  • Avoid vague words like "fast", "user-friendly", or "modern" — those belong in non-functional requirements.
  • Number every requirement (FR-01, FR-02...) so it can be referenced and tracked.

5 Non-Functional Requirements

Non-functional requirements (NFRs) define the quality attributes of the system — how well it performs its functions, not just what it does. They are often called "-ilities" because many end in that suffix.

Performance

NFR-01: The system shall load any page within 3 seconds on a standard broadband connection.

Security

NFR-02: All user passwords shall be hashed using bcrypt before being stored in the database.

Scalability

NFR-03: The system shall support up to 500 concurrent users without degradation in response time.

Accessibility

NFR-04: The system shall comply with WCAG 2.1 Level AA accessibility standards.

Reliability

NFR-05: The system shall have an uptime of at least 99.5% per calendar month.

Maintainability

NFR-06: All backend code shall include inline documentation and follow PEP 8 style guidelines.

Common mistake: Writing an NFR without a measurable number. "The system shall be fast" is not a valid NFR. "The system shall respond within 2 seconds" IS valid — because a tester can measure it.

6 Step-by-Step Writing Guide

Follow these steps every time you need to write an SRS document for a project:

Step 1 — Understand the Project. Talk to your client or product owner. Ask: Who are the users? What problem does this solve? What already exists? What is out of scope?
Step 2 — Define the Scope. Write a short paragraph that says what the system WILL do and what it will NOT do. This prevents "scope creep" — clients asking for more features mid-project.
Step 3 — Identify User Classes. Who uses this system? E.g., Student, Facilitator, Admin. Each class may have different permissions and features — document them separately.
Step 4 — List Functional Requirements. For each user class, list every feature. Use the FR-XX format. Think: registration, login, dashboard, data input, reports, notifications.
Step 5 — List Non-Functional Requirements. Consider: performance, security, reliability, accessibility, compatibility. Add measurable targets to each.
Step 6 — Review and Sign Off. Share the document with the client and team. Both parties must agree and sign it before development begins.

8 Real-World Example: SheLearn App

Let's apply everything above to a real project — the SheLearn web application itself. Here is a partial SRS written for it:

SRS — SheLearn Learning Platform Version: 1.0 | Date: March 2026 ───────────────────────────────────────────── 1. INTRODUCTION 1.1 Purpose This document defines the requirements for SheLearn, an e-learning platform for African female students studying technology. 1.2 Scope SheLearn WILL: host lessons, quizzes, student dashboards, facilitator tools, and track-based content routing. SheLearn WILL NOT: handle payment processing or video streaming in version 1.0. ───────────────────────────────────────────── 2. USER CLASSES Student – can view lessons, take quizzes, track progress Facilitator – can view, edit, and upload lesson materials Admin – can manage all users and system settings ───────────────────────────────────────────── 3. FUNCTIONAL REQUIREMENTS Authentication FR-01: The system shall allow new users to register with name, email, password, region, and chosen track. FR-02: The system shall redirect users to a track-specific dashboard after successful registration. FR-03: The system shall allow registered users to log in using email and password. Content Delivery FR-04: The system shall display lesson content specific to the student's enrolled track. FR-05: The system shall allow facilitators to edit lesson content through a secure edit toolbar. FR-06: The system shall allow facilitators to upload new lesson materials via the facilitator panel. Assessments FR-07: The system shall present knowledge-test quizzes to Data Science track students. FR-08: The system shall display quiz results immediately after submission. ───────────────────────────────────────────── 4. NON-FUNCTIONAL REQUIREMENTS NFR-01 (Performance): Pages shall load within 3 seconds. NFR-02 (Security): Passwords shall be hashed with bcrypt. NFR-03 (Scalability): System shall support 200 concurrent users. NFR-04 (Accessibility): UI shall meet WCAG 2.1 Level AA.

What you just learned

  • An SRS is the blueprint written before any code is created.
  • Functional requirements say what the system does; non-functional say how well it does it.
  • Every requirement needs a unique ID and must be testable.
  • Use "shall" for mandatory requirements — not "should" or "will".
  • The SRS is a shared agreement — all stakeholders must review and sign off.
  • Following IEEE 830 gives your document a professional, universal structure.
