1 What is Software Design?

Software design is the process of defining the architecture, components, modules, interfaces, and data of a system to satisfy specified requirements. It is the blueprint of your application — the plan before the code.

Think of it like building a house: Before laying any bricks, an architect creates detailed floor plans and blueprints. Software design is exactly that — you plan the structure of your system before writing a single line of code. This saves enormous time and prevents costly mistakes later.

Good design answers three fundamental questions: What will the system do? How will the pieces be organized? and How will the pieces talk to each other?

Why Software Design Matters

  • Helps teams communicate and agree on a system before building it
  • Reduces bugs by catching structural flaws early
  • Makes systems easier to maintain and extend over time
  • Provides documentation that outlives the original developers
  • Enables parallel development — different teams work on different parts simultaneously

2 Types of Software Design

Software design operates at different levels and focuses. There are two main levels — high-level (architectural) design and low-level (detailed) design — and within each, several named approaches:

Architectural Design Patterns

These define the overall structure and organisation of an entire system.

Monolithic Architecture

The entire application is built as a single, unified unit. Simple to develop initially, but hard to scale or update individual parts without affecting the whole system.

Layered (N-Tier) Architecture

The system is divided into layers — e.g., Presentation, Business Logic, and Data layers. Each layer only communicates with the one directly above or below it. Clean and easy to maintain.

MVC (Model-View-Controller)

Separates an app into three roles: the Model (data), the View (UI), and the Controller (logic connecting them). Used heavily in web frameworks like Django and Flask.

Microservices Architecture

The system is split into many small, independent services that each do one thing and communicate over APIs. Highly scalable, but more complex to manage. Used by Netflix, Amazon, and Uber.

Event-Driven Architecture

Components communicate by producing and responding to events rather than calling each other directly. Common in real-time systems like chat apps and IoT platforms.

Client-Server Architecture

A server provides resources or services, and clients request them. This is the backbone of the web — your browser is a client, and the website's backend is the server.

Object-Oriented Design Patterns

These are reusable solutions to commonly occurring problems within object-oriented code. They are grouped into three families:

Creational Patterns

Deal with how objects are created. Examples: Singleton (only one instance of a class exists), Factory (a method decides which class to instantiate), Builder (construct complex objects step by step).

Structural Patterns

Deal with how classes and objects are composed to form larger structures. Examples: Adapter (makes incompatible interfaces work together), Facade (provides a simple interface to a complex system).

Behavioral Patterns

Deal with how objects communicate and share responsibilities. Examples: Observer (when one object changes, all dependents are notified), Strategy (swap algorithms at runtime), Iterator (traverse a collection uniformly).

Quick rule of thumb: Architectural patterns describe the layout of a city (where roads, buildings, and utilities go). Design patterns describe the design of individual rooms inside those buildings — smaller, reusable solutions inside a larger structure.

3 Introduction to UML

UML (Unified Modeling Language) is a standardised visual language for describing, designing, and documenting software systems. It was created in the 1990s and is maintained by the Object Management Group (OMG). UML is not a programming language — it is a notation system, like musical notation is for composers.

UML gives developers, designers, and stakeholders a shared visual vocabulary. A diagram drawn in Berlin should be understood the same way in Nairobi or Tokyo, because UML is an international standard.

Two Main Families

Structural diagrams show the static parts of a system — what exists and how things are related.

Behavioral diagrams show the dynamic parts — how things move, change, and interact over time.

14 Diagram Types

UML 2 defines 14 official diagram types. In practice, most teams use a core set of 5–7. You'll learn the most important ones in this lesson.

Tools You Can Use

Draw.io (free), Lucidchart, StarUML, Visual Paradigm, PlantUML (code-based), or even pen and paper for quick sketches.

When Do You Draw UML?

  • During requirements analysis — Use Case diagrams to capture what the system must do
  • During system design — Class and Component diagrams to plan structure
  • During detailed design — Sequence diagrams to plan interactions between components
  • For documentation — to help new team members understand an existing system

4 Structural UML Diagrams

Structural diagrams answer the question: "What does the system consist of?" They are snapshots — they show the static architecture of a system at a point in time.

Structural

Class Diagram

The most widely used UML diagram. It shows the classes in a system, their attributes (data they hold), their methods (what they can do), and the relationships between them — such as inheritance, association, and composition.

Every class is drawn as a rectangle divided into three sections: the class name at the top, attributes in the middle, and methods at the bottom.

  • Used during the design phase to plan the objects in your codebase
  • Relationships: Association (uses), Inheritance (is-a), Composition (owns), Dependency (depends on)
  • Visibility markers: + public, - private, # protected
┌──────────────────────────┐ │ Student │ <<Class Name>> ├──────────────────────────┤ │ - studentId : int │ <<Attributes>> │ - name : String │ │ - email : String │ ├──────────────────────────┤ │ + enroll() : void │ <<Methods>> │ + getGrade(): float │ └──────────────────────────┘ │ inherits ┌──────────────────────────┐ │ GraduateStudent │ ├──────────────────────────┤ │ - thesisTopic : String │ ├──────────────────────────┤ │ + submitThesis(): void │ └──────────────────────────┘
Structural

Object Diagram

An object diagram is a snapshot of a class diagram at a specific moment in time. Where a class diagram shows the template, an object diagram shows real instances with actual values. Think of it as a class diagram filled in with data.

  • Useful for showing a specific scenario or state your system can be in
  • Objects are written as objectName : ClassName (underlined)
  • Helps validate that your class design works with real data
┌─────────────────────────────┐ │ harmony : Student │ <<Object instance>> ├─────────────────────────────┤ │ studentId = 1042 │ <<Actual values>> │ name = "Harmony Aisha" │ │ email = "h@shelearn.io" │ └─────────────────────────────┘
Structural

Component Diagram

Shows the high-level components (modules, services, libraries) of a system and how they are wired together through interfaces. A component is any replaceable part of a system that does a defined job.

This diagram is especially useful when designing large systems with multiple services (like a microservices application), showing which components depend on which.

  • Components are drawn as rectangles with a small component icon (two small rectangles) in the corner
  • Interfaces are shown as "lollipop" (provided) and "socket" (required) notations
  • Helps teams understand boundaries and responsibilities between parts of the system
┌────────────────┐ API calls ┌─────────────────┐ │ Frontend UI │ ─────────────────► │ Backend (Flask) │ │ (Browser) │ │ │ └────────────────┘ └────────┬────────┘ │ queries ┌────────▼────────┐ │ Database │ │ (PostgreSQL) │ └─────────────────┘
Structural

Deployment Diagram

Shows the physical infrastructure of a system — which software runs on which hardware or cloud environment. It maps software components (artifacts) to deployment nodes (servers, devices, cloud services).

  • Nodes are drawn as 3D boxes representing physical or virtual machines
  • Artefacts (deployable files like .jar, .py, .html) sit inside nodes
  • Critical for DevOps, cloud planning, and understanding how a system is hosted
  • Shows communication paths between nodes (HTTP, TCP, database connections)
┌─────────────────────────┐ HTTPS ┌────────────────────────┐ │ <<Node>> │ ◄──────────────── │ <<Node>> │ │ Web Server (Render) │ │ User's Browser │ │ ┌───────────────────┐ │ └────────────────────────┘ │ │ app.py (Flask) │ │ │ └───────────────────┘ │ SQL ┌────────────────────────┐ │ │ ────────────────► │ <<Node>> │ └─────────────────────────┘ │ Database Server │ └────────────────────────┘

5 Behavioral UML Diagrams

Behavioral diagrams answer the question: "How does the system behave?" They show how the system changes over time, how users interact with it, and how components talk to each other during different operations.

Behavioral

Use Case Diagram

The most accessible UML diagram — designed to be understood by non-technical stakeholders too. It shows actors (users or external systems) and the use cases (actions or goals) they can perform within the system.

Use Case diagrams do not show how something happens, only what actors can do. They are typically created first, during the requirements phase.

  • Actors are drawn as stick figures; use cases as ovals inside a system boundary rectangle
  • Lines connect actors to the use cases they participate in
  • <<include>> — one use case always calls another (like login always checks password)
  • <<extend>> — one use case optionally extends another (like a payment optionally triggering a receipt)
┌──────────────────────────────────────────┐ │ SheLearn System │ │ │ [User] ──── Sign Up │ [User] ──── Log In │ [User] ──── View Lesson ────<<include>>──── Authenticate [User] ──── Take Quiz │ │ │ [Facilitator] ─── Create Lesson │ [Facilitator] ─── View Student Progress │ └──────────────────────────────────────────┘
Behavioral

Sequence Diagram

One of the most powerful and commonly used UML diagrams. It shows how objects interact with each other over time — specifically the sequence of messages passed between them to complete a single operation or scenario.

Time flows downward. Each participant (object or system component) has a vertical "lifeline." Horizontal arrows between lifelines represent messages (function calls, API requests, etc.).

  • Shows the exact order of interactions — perfect for designing a login flow, checkout process, or API call chain
  • Solid arrows = calling a method; dashed arrows = returning a value
  • Activation bars (thin rectangles on the lifeline) show when an object is actively doing work
Browser Flask App Database │ │ │ │── POST /login ───►│ │ │ │── SELECT user ─►│ │ │◄─ user row ─────│ │ │ │ │ │ (check password)│ │ │ │ │◄── 200 + token ───│ │ │ │ │ │── GET /dashboard ►│ │ │◄── dashboard HTML ┤ │
Behavioral

Activity Diagram

An activity diagram is essentially an advanced flowchart. It models the step-by-step flow of activities in a process — including decisions (if/else branches), loops, and parallel actions.

Unlike sequence diagrams (which focus on interactions between objects), activity diagrams focus on the workflow of a single process, such as what happens when a user submits a form or when an order is processed.

  • Starts with a filled black circle (initial node) and ends with a filled circle inside a ring (final node)
  • Activities are rounded rectangles; decisions are diamonds with conditions on outgoing arrows
  • Can use swimlanes to show which actor or component is responsible for each step
● (Start) │ ▼ [ User fills Sign Up form ] │ ▼ ◇ All fields valid? │ No ──► [ Show error flash message ] ──► (loop back) │ Yes ▼ [ Hash password ] │ ▼ [ Save user to database ] │ ▼ [ Flash success message ] │ ▼ [ Redirect to dashboard ] │ ▼ ⊙ (End)
Behavioral

State Machine Diagram

A state machine diagram models the lifecycle of a single object — all the different states it can be in and the transitions (triggered by events) between those states. It answers: "What states can this object exist in, and what causes it to change?"

It is ideal for objects whose behaviour changes significantly depending on their current state, like a user account, an order, or a connection.

  • States are drawn as rounded rectangles; transitions are arrows with event labels
  • Guard conditions in square brackets restrict when a transition can fire: [balance > 0]
  • Entry and exit actions can be defined inside each state
  • Common uses: traffic lights, vending machines, user account status, order tracking
● │ ▼ ┌─────────────┐ verify email ┌──────────────┐ │ Registered │ ────────────────► │ Active │ └─────────────┘ └──────┬───────┘ │ violates policy ▼ ┌──────────────┐ │ Suspended │ └──────┬───────┘ │ appeal approved ▼ ┌──────────────┐ │ Active │ (restored) └──────────────┘

6 When to Use Which Diagram

You don't need every UML diagram for every project. Choose the right tool for the right question:

"What can users do?"

→ Use Case Diagram
Draw this first, during requirements gathering. Share it with stakeholders.

"What classes and relationships will I code?"

→ Class Diagram
Draw this during system design to plan your objects and database structure.

"How does this specific feature work, step by step?"

→ Sequence Diagram
Draw this to plan the messages between components for one scenario.

"What is the full workflow for this process?"

→ Activity Diagram
Draw this to map out branching logic in a business process or user journey.

"What states can this object be in?"

→ State Machine Diagram
Draw this for objects with complex lifecycle behaviour, like orders or accounts.

"How is the system deployed to servers?"

→ Deployment Diagram
Draw this when planning cloud infrastructure or explaining hosting to a DevOps team.

Key Takeaways

  • Software design is the blueprint — always design before you build
  • Architectural patterns (MVC, Microservices) define the big picture; design patterns solve specific smaller problems
  • UML is a shared visual language — it makes your design communicable to any developer worldwide
  • Class diagrams describe structure; sequence diagrams describe interaction; activity diagrams describe flow
  • Use Case diagrams are the best tool for communicating requirements to non-technical stakeholders
  • You don't need all 14 UML diagrams — pick the ones that answer your current question
Tip: Diagrams don't have to be perfect to be useful. A quick hand-drawn sketch on paper that your team can discuss is far more valuable than spending days on a perfectly formatted diagram that arrives too late to influence the design.
